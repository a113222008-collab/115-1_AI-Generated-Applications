## 一、自己的問題與設計

| 項目 | 我的內容 |
|---|---|
| App 名稱／作者 | 社團活動公告整理器／周沛妤 |
| 目標使用者與情境 | 想參加社團活動的大學生，在 LINE／IG／Email 看到一長串雜亂公告，想快速知道要做什麼、何時截止 |
| 想完成的一個任務 | 把貼上的公告原文整理成可行動的重點（要做什麼、何時截止、哪些資訊沒寫） |
| 輸入資料與範圍 | 一段公告原文，上限 6000 字；空白或超過上限不送出請求 |
| 資訊不足如何處理 | 只依原文整理、不補造；字串欄位填「原文未提及」，清單欄位回空清單；缺口列入 `missing_info`，建議私訊幹部詢問 |
| 採用 starter 或自行實作 | 採用課堂 starter 並改造。理由：starter 已有輸入檢查、錯誤處理與離線測試架構，可把時間放在題目與欄位設計 |

## 二、輸出欄位契約

至少兩個有用途的欄位；可自行加列。

| 欄位名稱 | 型別／限制 | 用途 | 畫面標籤 | 如何查原文 |
|---|---|---|---|---|
| event_name | str，必填 | 確認是不是要找的活動 | 活動名稱 | 展開「對照原文」，比對公告標題 |
| when_where | str，必填 | 判斷自己能不能去 | 時間與地點 | 比對原文的日期、時間、地點 |
| action_items | list[str]，必填 | 逐項照做（報名、繳費、帶東西） | 我需要做什麼 | 逐項在原文找到對應句子 |
| deadlines | list[str]，必填 | 排進行事曆，避免錯過 | 截止時間 | 比對原文截止日期與時間 |
| missing_info | list[str]，必填 | 私訊幹部詢問缺漏項目 | 公告沒寫、需要再問的事 | 確認列出的缺漏原文確實沒寫 |

真實 API 每筆補：測試日期、模型、完整虛構原文、實際 JSON／畫面結果、人工核對與實際請求數。
同一情境的修正前後用同一筆資料比較；不預設改 prompt 必然改善。不要用固定假回應填「真實 API」。

正常／資訊不足兩筆可直接在雲端完成，不必本機再重複呼叫；至少一筆須為雲端真實API成功。若追加測試，須另計請求數。
